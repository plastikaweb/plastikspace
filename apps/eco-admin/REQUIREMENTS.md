## 1. Context & goal

**Eco Store** is a multi-tenant SaaS e-commerce for ecological consumer cooperatives (first production tenant: Associació El Llevat). The public storefront (`apps/eco-store`) is member-facing only. Everything operational — managing products, orders, cycles, members, tenant configuration — is done today **directly in the PocketBase superuser console**.

**eco-admin exists to replace the PocketBase console for business operations.** The console remains a developer tool for schema management; every recurring operator task moves to eco-admin. This is not speculative: eco-store's own planning docs mark each of these gaps with the pattern _"Interim (no eco-admin yet) → superuser console"_ (`TASKS:L233`, `L248`, `L259`, `BACKLOG:L77`), and its Phase 1 exit criteria already assume a capability this app provides: _"account exit request (**deletion executed by the tenant admin**)"_ (`BACKLOG:L65`).

**eco-admin is currently unplanned.** The three tasks explicitly tagged eco-admin (PRV-05a MUST, TRL-07 MUST, TRL-09 SHOULD) appear in **zero** BACKLOG phases. The ~73.5 dev-day eco-store plan contains no admin work. This document is the starting point for that plan.

### 1.1 In scope

- A new Angular application `apps/eco-admin` in this monorepo, backed by the **same PocketBase instance** as eco-store.
- Both admin personas in v1, served by a **single app with role-partitioned navigation** — the two roles share the shell and almost no screens. Tenant Admin layer deliverable first (see §8 phases).
- All admin-side responsibilities currently marked "interim" plus the documented gaps no app owns today (§4).

### 1.2 Out of scope

- Schema management, migrations, hook deployment — stays in the PocketBase console / repo workflow.
- Any `PARTNER`-facing feature — that is eco-store.
- Payment processing (no payment gateway exists in the platform).
- Fixing eco-store security holes (PRV-05b-A closes `users.createRule`/`updateRule`) — eco-admin **depends on** that fix but does not implement it (§5.2).

## 2. Personas & role model

### 2.1 Personas

| Persona          | Role value     | Who                                              | Core jobs                                                                                                                                                     |
| ---------------- | -------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Tenant Admin** | `TENANT_ADMIN` | Cooperative operator (El Llevat volunteer/staff) | Weekly cycle ops: prepare orders, manage catalog & stock, process member requests, open/close store, convert trials                                           |
| **Superadmin**   | `GLOBAL_ADMIN` | Platform owner (Carlos)                          | Tenant lifecycle (onboarding, branding, platform kill-switch), tenant-admin account management, global catalogs. **No access to tenant-internal data** (§2.2) |

### 2.2 Role model — decision

**Use `users.role`, not `_superusers`.** The schema already defines `users.role: PARTNER | TENANT_ADMIN | GLOBAL_ADMIN` and — decisively — **almost every collection already carries role-aware API rules** for both admin roles (§3). `_superusers` tokens bypass API rules and hooks entirely (including the `x-bypass-hooks` escape), have no tenant scoping, and would make eco-admin a footgun. The superuser account stays where it belongs: the developer console.

**Privacy boundary (decision 2026-08-10).** `GLOBAL_ADMIN` administers **tenants**, not **tenant data**. Members, products, orders, carts, cycles, addresses, fiscal profiles, allowlists and requests are visible and manageable **only** by that tenant's `TENANT_ADMIN`. The Superadmin's reach is: the `tenants` collection, the global catalogs (§4.10), and the tenant-admin accounts themselves (narrow B-08 exception — never `PARTNER`s). This is data minimization by design: the platform owner has no business need to see a cooperative's member PII or commercial activity. Two consequences are accepted explicitly: cross-tenant analytics over live data is out (§4.10), and deep incident support (data surgery inside a tenant) stays in the superuser console, deliberately outside eco-admin.

Consequences:

- eco-admin logs in against the same `users` auth collection with `PocketBaseAuthService` (shared lib, already built).
- A **role guard** (`CanActivateFn`) and `isTenantAdmin` / `isGlobalAdmin` computeds must be added to `pocketBaseUserProfileStore` — today only logged-in/logged-out guards exist (§7).
- `PARTNER` users must be rejected at login with a clear message (they have valid credentials — the storefront uses the same accounts).

### 2.3 Tenant context

- **Tenant Admin:** tenant is fixed by `@request.auth.tenant`; the API rules enforce same-tenant access on every collection. The UI never offers a tenant switch.
- **Superadmin:** no persistent context switch — **the cooperative list is the selector and the tenant fitxa is the record screen** (round 17.2; the earlier «tenant selector» idea over-implied backend entry). GA never enters a tenant's operational modules, and no member-derived figure renders at L2 (an «Admins» TA-account count may — it is GA-managed under B-08).
- ⚠️ eco-admin must not reuse `provideEcoStoreTenant` (host-based, `scope:eco-store`); it needs its own tenant-context store (§7).

### 2.4 Deployment & routing — decision

**Single dedicated origin for both roles: `admin.9botiga.top`** (final hostname pending the AQ-05 hardening review). One deployment; after login the app partitions by role — a TA's tenant comes from the auth token (`@request.auth.tenant`), a GA gets the platform layer. The login screen is neutral; tenant branding applies post-login for TAs.

Rejected alternatives:

- **`/admin` path under the storefront hosts** (`el-llevat.9botiga.top/admin`): forces the storefront CF worker to route a second app (its asset-routing is already a known trap), shares origin storage with the shop — the PocketBase auth token in localStorage collides for a tenant admin who also shops as a member — and couples the two apps' CSP/headers/deploy cadence.
- **Per-tenant admin subdomains**: tenant identity already travels with the auth token, so per-tenant hosts add DNS/cert/deploy surface for zero functional gain; pre-login branding is not worth it.

### 5.2 Hard dependency — security blockers (owned by eco-store PRV-05b-A)

eco-admin's authorization model rests on `users.role` being trustworthy. Today it is not:

1. `users.createRule = ""` — anonymous signup with **arbitrary `role` and `tenant`**.
2. `users.updateRule` self-branch has no body constraints — _"any authenticated PARTNER can PATCH their own `role`/`tenant` today"_ (`TASKS:L253`).

**Gate:** eco-admin must not be deployed to any shared environment until PRV-05b-A lands (`@request.body.role:isset = false && @request.body.tenant:isset = false` on the self branch + gated create). Local development may proceed in parallel.

### 5.4 Explicitly (almost) no new backend

No new collections are required for Layer 1 beyond what eco-store already plans (`member_allowlist`, `tenant_requests`). eco-admin v1 requires **exactly one hook**, `on_request_reply.pb.js` (§5.6), which ships **in eco-store** (NOT- family, ID to be assigned in eco-store's TASKS.md) because it serves the public-form loop as much as the admin. Amended in v0.4.0 (was "zero hooks"): design rounds 4.1d–4.1g showed that the RGPD acknowledgment and the signup approval need a _recorded_ reply, and `mailto:` cannot record anything. Anything needing a new collection lives in Layer 3.

### 5.5 Audit trail (open requirement — AQ-03)

`tenant_requests` records who processed what (`processedBy`/`processedAt`) and — since v0.4.0 — what was said to the requester and when (`reply`, `repliedAt`, `plannedExecutionAt`, `resolutionNote`): a complete trail for AREQ. Membership transitions, deletions, config changes still have no authorship trail — and `membershipStatus` stays self-writable (§4.6). Options: (a) minimal `admin_audit` collection written by eco-admin on sensitive mutations; (b) PocketBase hook-based logging; (c) defer. **Recommendation: (a), scoped to AMBR-03/07 and ACFG-07 mutations only.** Decision pending.

### 5.6 `tenant_requests` contract (design rounds 4.1c–4.1g)

The collection does not exist yet in `pb_schema.json` — it ships with eco-store PRV-08 (`TASKS:L234`). This is the contract eco-admin builds against; **it must be synced into the PRV-08 spec before the collection is created** (owner: eco-store TASKS.md, same mechanism as B-07). Everything below is derived from the frozen 4.1g design and the PocketBase rules verified in this workspace.

**Fields** (beyond `type`, `status`, `name`, `email`, `message`, `tenant`, `processedBy`, `processedAt`, `created`):

| Field                | Type                                        | Why                                                                                                                                                                                                                                                                                           |
| -------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `user`               | relation → `users`, `cascadeDelete = false` | **Resolved server-side in the PRV-08 create hook** (lookup by email). Reactivation match ("coincideix amb un soci inactiu") and "orders since the request" then work without email filtering on `users` — no dependency on B-11, and the public caller learns nothing (no enumeration oracle) |
| `language`           | select `ca/es/en` (like `orders.language`)  | The reply hook localizes subject/footer; the dialog prefills templates in the requester's language                                                                                                                                                                                            |
| `reply`              | text                                        | Latest reply text sent to the requester (AREQ-07). Overwritable only on `ACCOUNT_DELETION` (re-date)                                                                                                                                                                                          |
| `repliedAt`          | date                                        | **First** reply — immutable once set; the timestamp that counts for art. 12.3                                                                                                                                                                                                                 |
| `plannedExecutionAt` | date, nullable                              | `ACCOUNT_DELETION` only; interpolated into the reply and driving the AREQ-09 chip                                                                                                                                                                                                             |
| `resolutionNote`     | text                                        | Dismiss reason (mandatory on `ACCOUNT_DELETION`, optional otherwise); optional note on `MEMBERSHIP_TERMINATION`                                                                                                                                                                               |

**API rules** (no `GLOBAL_ADMIN` branch — B-07):

- `create = ""` (public forms) **with body constraints**: `@request.body.status:isset = false && @request.body.processedBy:isset = false && @request.body.reply:isset = false && @request.body.repliedAt:isset = false && @request.body.tenant != ""`.
- `list / view`: `@request.auth.role = "TENANT_ADMIN" && tenant = @request.auth.tenant`.
- `update`: same tenant/role, plus the guards — `(@request.body.status:isset = false || (status = "PENDING" && @request.body.processedBy = @request.auth.id))` (a request leaves PENDING once, stamped by whoever does it — AREQ-03) · `(@request.body.repliedAt:isset = false || repliedAt = "")` (first reply immutable) · `(@request.body.reply:isset = false || reply = "" || type = "ACCOUNT_DELETION")` (double reply blocked except RGPD re-date). A guard failure returns **404** — the UI treats it as a concurrency conflict (AREQ-09).
- `delete = null` (locked): requests are never deleted — Resolts is the accountability record (retention of DISMISSED spam → AQ-12).

**Indexes** (B-09 extended): `(tenant, status, created)` for the oldest-first trays; `(tenant, email)` for search and prior-request lookups.

**Hook `on_request_reply.pb.js`** (eco-store, NOT- family): `onRecordAfterUpdateSuccess("tenant_requests")` when `reply` **or** `plannedExecutionAt` changed → mail to `email` with the reply text (+ planned date), subject/footer by `language` and `type`; `From` = platform sender (one SMTP sender per PocketBase instance; the transactional provider requires a verified domain), `Reply-To` = `tenants.email` (ACFG-03) — "en nom de la cooperativa" means exactly this, not a `From` on the cooperative's domain; **no send if `email` is masked/empty**. Idempotent on repeated identical writes.

**Masking on execution** (pending AQ-10): if the decision is "mask", it belongs in the PRV-08 `on_delete_user` hook over the deleted user's `tenant_requests` rows — server-side, same transaction — not a second write from eco-admin. Sequence in the UI: reply → execute → mask; nothing is sent after the mask.

**Instance settings & hardening:** enable the **Batch API** (off by default) — "Anul·la la comanda i executa" is one transaction (cancel `orders` + delete `users`; a 409 from `on_delete_user` rolls the cancel back) · **rate limit** on `POST /api/collections/tenant_requests/records` (per IP) + a honeypot field in the public forms — otherwise "hundreds of messages" is literal.

### 5.7 `member_allowlist` contract (design round 8)

The collection does not exist yet in `pb_schema.json` — no migration references it. It ships with eco-store **PRV-05b** under the same **G-02** gate as `tenant_requests`, and it needs the same treatment: **this contract must be synced into the PRV-05b spec before the collection is created**. Without it, PRV-05b can ship a bare address list and the AMBR-04 states, the "Ús" column and the CSV import all collapse at build time. Unlike the members tab, this one is **not** blocked by B-11 — `member_allowlist.email` is a plain field on a base collection, not the hidden `email` of an auth collection.

**Fields**

| Field       | Type                                        | Why                                                                                                                                                                                                                                                   |
| ----------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tenant`    | relation → `tenants`, required              | Scoping. UNIQUE together with `email`                                                                                                                                                                                                                 |
| `email`     | email, required                             | The invitation itself. Registration checks it server-side — **never through a public pre-check endpoint** (that would be a census oracle)                                                                                                             |
| `notes`     | text, max 140                               | Why this address was invited ("llista d'espera", "aval"). **Minimisation applies** — see below                                                                                                                                                        |
| `usedAt`    | date, nullable                              | Stamped by the PRV-05b registration flow when the account is created. Drives the `CONSUMED` state and the "Ús" column                                                                                                                                 |
| `user`      | relation → `users`, `cascadeDelete = false` | Set in the same registration write. Expanded to render the member's `name` in the "Ús" column — readable by a TA (`users.listRule` allows same-tenant TA and `name` is not the auth-hidden `email`)                                                   |
| `revoked`   | bool, default false                         | Drives the `REVOKED` state. Blocks future registration without touching existing accounts and without losing the trace                                                                                                                                |
| `revokedAt` | date, nullable                              | Round 8.1: with a boolean alone a restored row is indistinguishable from one never revoked, and the delete dialog's «sense perdre l'historial» would be untrue. Set on revoke, cleared on restore; add `revokedBy` only if AQ-03 lands an audit model |

**The three UI states are derived, never stored** (AMBR-04): `PENDING` = neither `usedAt` nor `revoked` · `CONSUMED` = `usedAt` set · `REVOKED` = `revoked` set. No status enum — the builder must not add one.

**API rules** (no `GLOBAL_ADMIN` branch — B-07): `list / view / create / update / delete` all `@request.auth.role = "TENANT_ADMIN" && tenant = @request.auth.tenant`. **No public rule of any kind**: the registration check runs inside the PRV-05b hook with superuser context, so a prospective member can never probe whether an address is on the list.

**Deletion semantics.** `revoke` and `delete` are different actions and both need the §3.6 confirm: revoke keeps the row and is reversible; delete destroys the trace and lets the address be re-invited from scratch. A `CONSUMED` row cannot be deleted from the UI while `user` still points at an account.

**Erasure (PRV-08) — the open half, folded into AQ-10.** AMBR-07 lists the post-delete consequences (`orders` scrubbed, addresses and fiscal profile cascade) and says nothing about this collection. Because `email` is a field of its own, executing an RGPD deletion today would leave the erased person's address — plus a free-text note and, through the relation, their name — in the cooperative's allowlist indefinitely. **Whatever AQ-10 decides for `tenant_requests` must be applied here in the same `on_delete_user` hook and the same transaction.** Recommended and consistent with the frozen 4.1g mock: mask `email`, null `user`, keep `usedAt` as the trace. The alternative (cascade-delete the row) silently re-opens registration for that address and must be a deliberate choice, not a default.

**`notes` minimisation.** The field routinely holds personal data about **third parties** — the design fixture alone carries "veïna de Marta Puig", "germana de Guillem Font", "aval: Núria Solé". Cap it at 140 characters, put a helper under the input saying what not to write (no health, financial or family details about anyone), and purge it with the row on erasure. No round has raised this before design round 8.

**Indexes:** UNIQUE `(tenant, email)` — it is also the duplicate check the add dialog and the CSV stepper rely on; `(tenant, usedAt)` and `(tenant, revoked)` for the state filters.

**CSV import** (AMBR-05, contract pinned in design round 8): columns `email` (required) · `nom` (optional) · `notes` (optional); UTF-8; max 1.000 rows; duplicates detected against the existing list and skipped without error; invalid rows reported and discarded; imported rows enter as `PENDING`. `nom` has nowhere to live in this collection — it is used only to help the operator recognise the row during review, or it needs a `name` field here; **decide before PRV-05b** (proposal: add `name`, text, optional, since the row exists before the account does).
